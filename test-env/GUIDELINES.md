## ინსტრუმენტები — ყოველდღიური ბრძანებები

**აწყობა და გაშვება (ხელით, ტესტის გარეშე):**

```
nasm -f elf64 -g -F dwarf prog.asm -o prog.o     # შეცდომა? ხაზს და სვეტს გაჩვენებს
ld prog.o -o prog                                # ლინკვა
./prog; echo "exit: $?"                          # გაშვება + exit code
```

**gdb — ყველაზე მნიშვნელოვანი ჩვევა:**

```
gdb -q solutions/w1d1_exit42
(gdb) b _start              # გაჩერდი დასაწყისში
(gdb) run
(gdb) stepi                 # ერთი ინსტრუქცია წინ
(gdb) info registers rax rdi rcx rdx
(gdb) p/x $rax              # 16-ობითში
(gdb) p/t $rax              # ორობითში (ბიტებისთვის!)
(gdb) p $rax                # ათობითში
(gdb) x/8cb &msg            # 8 ბაიტი მისამართიდან, სიმბოლოებად
(gdb) x/4gx $rsp            # სტეკის 4 რვაბაიტიანი სიტყვა
(gdb) layout regs           # რეგისტრები გვერდით, ცოცხლად
(gdb) quit
```

**გაშიფვრა (თუ gdb-ის სინტაქსი პირველად გხედავთ):**

- `$rax` — `$` ნიშნავს „ეს რეგისტრია“. `p $rax` = „დაბეჭდე `rax`-ის მნიშვნელობა“.
- `&msg` — `&` ნიშნავს „ეს მისამართია“. `x/8cb &msg` = „მაჩვენე 8 (`8`) ერთეული,
  თითო 1 ბაიტი (`b`), სიმბოლოებად (`c`), `msg`-ის მისამართიდან“.
- `x/4gx $rsp` — იგივე, მაგრამ 4 რვაბაიტიანი (`g`) მნიშვნელობა, hex-ად (`x`).
- `$rip` — „სად ვართ ახლა კოდში“; `$rsp` — „სად არის სტეკის თავი“ (ახსნები:
  [`../GLOSSARY.md`](../GLOSSARY.md) → `rip`, `rsp`).

**როგორ ვკითხულობ შეცდომებს:**

| სიმპტომი | სად ვეძებ მიზეზს |
| --- | --- |
| `nasm: error: ... line N` | ბრჭყალები, მძიმეები, ზომის შეუთავსებლობა (`mov rax, [msg]` vs `mov eax, ...`) |
| `ld: cannot find entry symbol _start` | აკლია `global _start` ან ლეიბლი `_start:` |
| `Segmentation fault` | მისამართი არასწორია, ან სექცია არასწორი (`.data`-ში წერა), ან `rsp` გატეხილი |
| `SIGFPE` | გაყოფა ნულზე, ან `div`-მდე `rdx` არ განულდა |
| exit code 0, მაგრამ შედეგი არასწორია | ციკლი არ შესრულდა / არასწორი შედარება |
| ტერმინალი ჩერდება | უსასრულო ციკლი — ტესტი 10 წამში წყვეტს, gdb-ში `Ctrl+C` |

# I კვირა

## w1d1_exit42 · exit 42

**სამიზნე:** პროგრამა, რომელიც მთავრდება კოდით 42.

**სცენარი:** არაფერი იკითხება, არაფერი იბეჭდება — მხოლოდ exit code.

**იდეები:**

1. Linux-ში პროგრამა ბირთვს ელაპარაკება **syscall**-ით. exit-ისთვის საჭიროა
   სამი რამ: რეგისტრი ნომრით, რეგისტრი არგუმენტით და თვითონ `syscall`.
2. ნახე ცხრილი `01-week1-fundamentals.md` § 5 — რომელი ნომერია `exit` და
   რომელ რეგისტრში მიდის არგუმენტი.
3. გახსოვდეს: `_start`-იდან თუ უბრალოდ „ჩამოვარდი“, პროგრამა ავარიულად
   სრულდება. ყოველი პროგრამა უნდა დასრულდეს განზრახ.

**gdb-ით გადამოწმება:** `stepi` გაიმეორე სამჯერ. ყოველ ნაბიჯზე `info registers rax rdi`.
ნახე: რომელ ბრძანებაზე ჩნდება 60 და რომელზე 42.

**ხშირი შეცდომები:**

- `global _start` დაგავიწყდა → ლინკერი ვერ პოულობს შესასვლელ წერტილს.
- `_start:` ლეიბლის ორწერტილი გამოტოვე.
- `mov rdi, 42` ნაცვლად `mov rax, 42` — ადგილები აირია, exit code ხდება 60 ან 0.

**დაფიქრდი:** რატომ ვერ დაბრუნებს exit code 300-ს? (პასუხი: 8 ბიტი.)

**წყარო:** `01-week1-fundamentals.md` § I დღე

## w1d2_arith · (5+3)*4-2 = 30

**სამიზნე:** იგივე პროგრამა, მაგრამ შედეგი გამოითვლება ინსტრუქციებით.

**სცენარი:** `a=5, b=3, c=4, d=2` → exit code 30.

**იდეები:**

1. ფრჩხილები ნიშნავს **თანმიმდევრობას**, არა სპეციალურ სინტაქსს. დაშალე:
   ჯერ ჯამი, მერე ნამრავლი, მერე გამოკლება.
2. rax არის „მთავარი“ რეგისტრი არითმეტიკისთვის, მაგრამ ყოველი ოპერაცია მას
   ცვლის — თუ დაკარგე, ვეღარ გაიხსენებ. ამიტომ შუალედური შედეგები
   შესამოწმებლად gdb-ში ნახე.
3. `add`, `sub`, `imul` — `imul`-ს ორი ოპერანდით იყენებ (რეგისტრი,
   რიცხვი ან რეგისტრი).

**gdb-ით გადამოწმება:** `stepi` ყოველ ინსტრუქციაზე და `p $rax`. დაწერე ქაღალდზე
მოსალოდნელი მნიშვნელობა **ყოველი** ნაბიჯის შემდეგ და შეადარე.

**ხშირი შეცდომები:**

- მხოლოდ ბოლო ოპერაცია შესრულდა (წინა შედეგი გადაიწერა).
- `imul` 3 ოპერანდით გამოიყენე და არგუმენტების რიგი აირია.

**დაფიქრდი:** რა მოხდებოდა, უარყოფითი რიცხვი რომ ყოფილიყო? რომელი

## w1d2_div_remainder · 100 / 7 — ნაშთი

**სამიზნე:** სცენარი, სადაც exit code-ად **ნაშთი** ბრუნდება.

**სცენარი:** 100 ÷ 7 → მთელი ნაწილი 14, ნაშთი 2 → exit code 2.

**იდეები:**

1. `div` მუშაობს **წყვილზე**: ერთი რეგისტრი იღებს მთელ ნაწილს, მეორე — ნაშთს.
   რომელია რომელი? ნახე § II დღის მაგალითი.
2. `div`-მდე **ზედა ნახევარი უნდა იყოს 0** — თუ იქ წინა ოპერაციის ნარჩენია,
   შედეგი არასწორი იქნება ან `SIGFPE` მოხდება.
3. გაყოფის შემდეგ **მხოლოდ** ნაშთი გამოიყენე exit code-ად.

**gdb-ით გადამოწმება:** `stepi` `div`-მდე — შეამოწმე `p $rdx` = 0.
`div`-ის შემდეგ `p $rax` = 14 და `p $rdx` = 2. ორივე ერთდროულად უნდა დაინახო.

**ხშირი შეცდომები:**

- `rdx` არ განულდა → SIGFPE.
- `div`-ს გადაეცა რიცხვი იმავე რეგისტრში, რომელსაც ანგრევს.
- ნაშთის ნაცვლად მთელი ნაწილი დაბრუნდა (14 → გამოვიდოდა 14, არა 2).

**დაფიქრდი:** რატომ არსებობს `idiv` ცალკე? რა იცვლება უარყოფითებზე
(დამრგვალება ნულისკენ, არა ქვემოთ)?

## w1d3_hello · „Hello“ write-ით

**სამიზნე:** ეკრანზე გამოიტანე ზუსტად `Hello`.

**სცენარი:** ტესტი იღებს გამოსავლის ბოლო არაცარიელ ხაზს → უნდა იყოს `Hello`.

**იდეები:**

1. `write` syscall-ს **ოთხი** პარამეტრი სჭირდება: გამოძახების ნომერი,
   ფაილის დესკრიპტორი (ეკრანი = 1), ტექსტის **მისამართი**, ბაიტების რაოდენობა.
   დააკავშირე `01-week1 § 5`-ის ცხრილს: რომელი რეგისტრი რომელია.
2. ტექსტი `.data`-ში ცხადდება (`db`), ხოლო მისამართი მოძრავი რეგისტრით
   იტვირთება — `msg` **თვითონ არის მისამართი**, `[msg]` კი მისი შიგთავსი.
3. სიგრძე ხელით ნუ დათვლი — NASM-ს შეუძლია თვითონ გამოთვალოს ლეიბლების
   სხვაობიდან (`equ $ - msg`).

**gdb-ით გადამოწმება:** `b _start`, `run`, `stepi` სანამ `syscall`-მდე მიხვალ.
შეამოწმე ოთხივე რეგისტრი `info registers`. შემდეგ `x/6cb &msg` — ნახე ბაიტები
და დარწმუნდი, რომ სიგრძე ზუსტად მათ რაოდენობას ემთხვევა.

**ხშირი შეცდომები:**

- `mov rsi, [msg]` — ტექსტის ნაცვლად პირველი 8 ბაიტი, როგორც რიცხვი.
- სიგრძე არასწორია (1 ბაიტით მეტი/ნაკლები) → აკლდება ასო ან ბეჭდება ნაგავი.
- `syscall`-ის შემდეგ პროგრამა არ გავიდა → ავარია `write`-ის შემდეგ.

## w1d4_sum_1_to_100 · 1-დან 100-მდე ჯამი

**სამიზნე:** ციკლი, რომელიც ითვლის 1+2+…+100 = 5050 და აბრუნებს მას.

**სცენარი:** exit code უნდა იყოს 186 (5050-ის დაბალი ბაიტი).

**იდეები:**

1. ციკლს სჭირდება **სამი** ნაწილი: საწყისი მნიშვნელობები, სხეული (ჯამის
   დამატება), და პირობა რომელიც ციკლს ხურავს. ერთი აკლდება და ციკლი ან
   არასდროს შესრულდება, ან არასდროს დამთავრდება.
2. `rcx` ბუნებრივი მთვლელია (ისტორიულად `loop` ინსტრუქციასთანაა
   დაკავშირებული), მაგრამ **ფრთხილად**: `syscall` ანგრევს `rcx`-ს. თუ ციკლის
   შიგნით `write`-ს იძახებ, სხვა რეგისტრი აირჩიე.
3. `cmp` მხოლოდ **ფლაგებს** აყენებს, არაფერს არ ცვლის. გადახტომა ცალკე
   ინსტრუქციაა (`jle`, `jne`, `jl`…). signed/unsigned აქ მნიშვნელოვანია.

**gdb-ით გადამოწმება:** `break` დააყენე ციკლის ლეიბლზე და ყოველ გავლაზე
`p $rax` და `p $rcx`. გამოთვალე: 100-ე გავლის შემდეგ rax უნდა იყოს 5050
(`p/x $rax` → `0x13ba`). exit code კი `5050 & 255`.

**ხშირი შეცდომები:**

- `rcx` 0-იდან დაიწყო → ჯამი 4950, exit code 134.
- პირობა ისეთია, რომ ციკლი ერთი ნაბიჯით ადრე/გვიან ჩერდება (off-by-one).
- ჯამი სწორია, მაგრამ `exit`-ს მთელი 5050 გადაეცა და „186“ ნაცვლად სწორედ
  ეგ არის მოსალოდნელი — ასე რომ გაითვალისწინე, ტესტი 186-ს ელოდება.
- უსასრულო ციკლი: `inc` ან პირობის განახლება გამოტოვე.

**დაფიქრდი:** გამოთვალე ჯამი ფორმულით (n(n+1)/2) — რამდენ ინსტრუქციას
ჭირდება ციკლი და რამდენს ფორმულა? რას ნიშნავს ეს ალგორითმის სირთულისთვის?

**წყარო:** `01-week1-fundamentals.md` § IV დღე

## w1d4_array_max · მასივის მაქსიმუმი

**სამიზნე:** იპოვე მასივის უდიდესი ელემენტი.

**სცენარი:** `dq 5, 17, -3, 42, 8` → exit code 42.

**იდეები:**

1. მაქსიმუმის ძებნა იწყება **პირველი ელემენტით** (0-ით დაწყება არასწორია
   უარყოფით მასივზე — სცადე და მიხვდები რატომ).
2. მისამართვა: `[base + index*scale]`. `dq` ნიშნავს 8-ბაიტიან ელემენტებს,
   ამიტომ scale = 8. `equ`-ით სიგრძე ლეიბლებიდან გამოთვალე.
3. შედარება **signed** უნდა იყოს, თორემ -3 `0xFFFFFFFFFFFFFFFD`-ის გამო
   ყველაზე „დიდი“ აღმოჩნდება. signed/unsigned გადახტომები: `jg/jl` vs `ja/jb`.

**gdb-ით გადამოწმება:** `x/5dg &arr` — ნახე მასივი ათობითში.
`b` დააყენე შედარებაზე და ყოველ გავლაზე ნახე `p $rax` (მიმდინარე max) და
`p $rdx` (მიმდინარე ელემენტი). ნახე, როდის ხდება განახლება.

**ხშირი შეცდომები:**

- max 0-იდან დაიწყე → უარყოფით მასივზე არასწორი პასუხი.
- `jl`/`jg` ნაცვლად `jb`/`ja` → -3 მაქსიმუმად ჩაითვალა.
- ინდექსი 0-იდან არის, მაგრამ ციკლი 1-იდან დაიწყე და პირველი ელემენტი
  გამოტოვე (ან პირიქით — `arr[5]`-ს წაიკითხავ, რაც მასივს გარეთაა).

**დაფიქრდი:** რა მოხდება, თუ ციკლი ერთი ელემენტით მეტს წაიკითხავს?
რატომ არ იძლევა ამას კომპილატორი შეცდომას Assembly-ში?

**წყარო:** `01-week1-fundamentals.md` § IV დღე

## w2d1_add_function · add(10, 20)

**სამიზნე:** ცალკე ფუნქცია, რომელსაც `call`-ით იძახებ.

**სცენარი:** `rdi=10, rsi=20` → დაბრუნდეს 30 → exit code 30.

**იდეები:**

1. System V AMD64-ის წესი: პირველი არგუმენტები რიგით რეგისტრებში მოდის
   (`rdi, rsi, rdx, rcx, r8, r9`), დაბრუნებული მნიშვნელობა — `rax`-ში.
   ნახე `02-week2 § II დღე`-ის ცხრილი.
2. `call` ავტომატურად დებს **დაბრუნების მისამართს** სტეკზე; `ret` მას იღებს.
   თუ ფუნქციაში `push` გააკეთე, `ret`-მდე `pop`-იც უნდა იყოს.
3. ფუნქცია `ret`-ით უნდა დასრულდეს. `rev`-ის შემდეგ დაწერილი კოდი არ
   შესრულდება.

**gdb-ით გადამოწმება:** `break` დააყენე შენი ფუნქციის ლეიბლზე და `run`.
`info registers rdi rsi` — არგუმენტები ადგილზეა? `x/4gx $rsp` — დაინახავ
დაბრუნების მისამართს სტეკის თავზე. `ret`-მდე `p $rax`.

**ხშირი შეცდომები:**

- `rsp` არ აღდგა → `ret` არასწორ მისამართზე გადახტება → segfault.
- არგუმენტები არასწორ რეგისტრებში წაიკითხე.
- პასუხი `rax`-ის ნაცვლად სხვა რეგისტრში დატოვე.
- `call`-ის ნაცვლად `jmp` გამოიყენე → `ret` ვერ დაბრუნდა.

**დაფიქრდი:** რატომ არსებობს გამოძახების კონვენცია საერთოდ? რა მოხდებოდა,
თითოეული ფუნქცია თვითონ რომ ირჩევდეს რეგისტრებს?

**წყარო:** `02-week2-stack-functions.md` § I დღე

## w2d2_factorial · factorial(5) = 120

**სამიზნე:** რეკურსიული ფუნქცია.

**სცენარი:** n=5 → 120 → exit code 120.

**იდეები:**

1. რეკურსიას სჭირდება **base case**, რომელიც აჩერებს: n ≤ 1 → 1. მის გარეშე
   სტეკი გადაივსება.
2. `rdi` **caller-saved**-ია: რეკურსიული გამოძახება მას გადაწერს. თუ მნიშვნელობა
   გჭირდება დაბრუნების შემდეგ — `push`/`pop` ან callee-saved რეგისტრი.
3. ყოველი გამოძახება ახალ „ჩარჩოს“ ქმნის სტეკზე. n=5 → 5 ჩარჩო ერთდროულად.

**gdb-ით გადამოწმება:** n=3-ზე გაუშვი და ყოველ `call`-ზე `x/8gx $rsp`.
დაინახავ, როგორ იზრდება სტეკი და როგორ შრინდება დაბრუნებისას. `bt`
(backtrace) გაჩვენებს ჩარჩოების ჯაჭვს — ეს რეკურსიის ვიზუალიზაციაა.

**ხშირი შეცდომები:**

- base case არასწორი (`jle`/`jl` აირია) → უსასრულო რეკურსია → segfault.
- `rdi` არ შენახა → ნამრავლი არასწორია, თუმცა პროგრამა „მუშაობს“.
- `pop`-ის რიგი აირია (push A, push B → pop B, pop A).
- `rbx` გამოიყენე და არ აღადგინე → caller-ის მონაცემები დაზიანდა.

**დაფიქრდი:** n=10-ზე რამდენ ბაიტს დაიკავებს სტეკი? გამოთვალე და შეადარე
`info frame`-ის შედეგს.

**წყარო:** `02-week2-stack-functions.md` § II დღე

2. `scasb` ადარებს `al`-ს `[rdi]`-ს და `rdi`-ს ზრდის. `repne` იმეორებს სანამ
   არ დაემთხვევა **ან** `rcx` არ გახდება 0. სწორედ ამიტომ `rcx`-ს თავიდან
   „უსასრულო“ მნიშვნელობა აძლევენ და სიგრძეს ბოლოს ითვლიან.
3. ხელით ვერსია უფრო გასაგებია: მაჩვენებელი წინ მიდის, ყოველ ნაბიჯზე
   ზომა იზრდება, გაჩერება — 0 ბაიტზე.
4. **Direction Flag**: თუ სადმე `std` გამოიყენე, `cld` აუცილებელია — თორემ
   სხვა ფუნქციები უკუღმა ივლიან.

**gdb-ით გადამოწმება:** `x/16cb $rdi` — დაინახავ NUL ბაიტს ბოლოს. ეს არის
„სიგრძის საზღვარი“. `info registers rcx rdi` გაჩვენებს სად გაჩერდა.

**ხშირი შეცდომები:**

- `rcx` არ დააყენე → `repne` ან მაშინვე ჩერდება, ან უსასრულოდ მიდის.
- ოფ-by-one: სიგრძე 10 ან 12 ნაცვლად 11-ისა (`scasb`-ის შემდეგ `rdi` ერთით
  წინაა).
- `al` არ განულდა — ადარებს წინა ოპერაციის ნაშთს, ამიტომ პირველივე ბაიტზე
  „ემთხვევა“.
- NUL-ის ნაცვლად `\n`-ს ეძებ.

**დაფიქრდი:** რატომ არის `repne scasb` თეორიულად უფრო სწრაფი ვიდრე ხელით
ციკლი, თუმცა ლოგიკურად იგივეს აკეთებს?

## w2d4_popcount · popcount(0b10110111) = 6

**სამიზნე:** დათვალე ერთიანი ბიტები.

**სცენარი:** `rax = 0b10110111` → exit code 6.

**იდეები:**

1. **პირველი გზა (ყველაზე გასაგები):** ციკლი, სადაც ბოლო ბიტს ამოწმებ
   (`test`/`and` 1-ზე), მერე რიცხვს მარჯვნივ წიაღწევ (`shr`) და ითვლი.
2. **მეორე გზა (ხრიკი):** `x & (x-1)` ყოველ ნაბიჯზე შლის **ერთ** ერთიანს.
   სცადე ხელით: 0b10110111 → 0b10110110 → … და დაითვალე ნაბიჯები.
3. **მესამე გზა:** CPU-ს `popcnt` ინსტრუქცია — ერთი ბრძანება. შეამოწმე,
   მხარს უჭერს თუ არა შენი პროცესორი (`grep popcnt /proc/cpuinfo`).

**gdb-ით გადამოწმება:** `p/t $rax` — ორობითი სახე. ხელით გადათვალე ერთიანები
და შეადარე. მეორე გზის შემოწმება: ყოველ ნაბიჯზე `p/t $rax` და ნახე, რომ
ზუსტად ერთი ერთიანი ქრება.

**ხშირი შეცდომები:**

- `shr` signed/unsigned არევა (`sar` vs `shr`) — აქედან გამომდინარე ყველა
  ბიტი 1-ად რჩება.
- ციკლი `rax == 0`-ზე არ ჩერდება → უსასრულო ციკლი.
- `x & (x-1)`-ის შედეგი ისევ `x`-ში ჩაწერე, მაგრამ მთვლელი არ გაზარდე.
- `popcnt` გამოიყენე CPU-ზე, რომელსაც არ აქვს → `Illegal instruction`.

**დაფიქრდი:** რამდენ ნაბიჯს აკეთებს პირველი გზა 0b10110111-ზე და რამდენს
მეორე? რა არის უარესი შემთხვევა თითოეულისთვის?

**წყარო:** `02-week2-stack-functions.md` § IV დღე

## w2d4_is_power_of_two · is_power_of_two(64) → 1

   შედეგი 0-ია, მხოლოდ ერთი ერთიანი იყო.
3. **Edge case 0:** 0-ს არც ერთი 1-იანი არ აქვს, ამიტომ ხრიკი მას
   „დადებითად“ ჩათვლის. 0 ცალკე უნდა გამორიცხო (და უარყოფითები, თუ signed
   მუშაობ).

**gdb-ით გადამოწმება:** ერთიანი ბიტების რაოდენობა ნახე `p/t $rax`-ით და
შეამოწმე შენი ფუნქცია **სამ** შემთხვევაზე: 64 (კი), 65 (არა), 0 (არა).
ტესტი მხოლოდ ერთს ამოწმებს — დანარჩენი შენი პასუხისმგებლობაა.

**ხშირი შეცდომები:**

- 0 დაუმუშავებელი დატოვე → არასწორად 1.
- `test`-ის ნაცვლად `and` გამოიყენე და ორიგინალი რიცხვი დაკარგე (ან პირიქით,
  შედეგი დაგჭირდა და ორიგინალი გადაწერე).
- უარყოფითი რიცხვი (`0x8000...`) ხარისხად ჩათვალე.

**დაფიქრდი:** რამდენი ბიტია 64-ში? რატომ არის `2^n` ყოველთვის ერთი
1-იანი ბიტი, მიუხედავად n-ისა?

## w2d4_xor_swap · xor-ით გაცვლა

**სამიზნე:** გაცვალე ორი რეგისტრის მნიშვნელობა დროებითი რეგისტრის გარეშე.

**სცენარი:** `rax=10, rbx=20` → გაცვლის შემდეგ exit code იყოს `rax` = **20**.

**იდეები:**

1. `xor`-ის თვისება: `a ^ a = 0` და `a ^ 0 = a`. სამი ნაბიჯი საკმარისია
   ორი მნიშვნელობის გასაცვლელად — იპოვე ისინი ლოგიკურად, არ დაიმახსოვრო.
2. წესრიგი **მკაცრია**. სცადე შუალედური ნაბიჯების ადგილების შეცვლა და
   მიხვდები, რატომ იშლება ყველაფერი.
3. **აკრძალული:** ერთი და იმავე რეგისტრზე `xor` → ორივე მნიშვნელობა 0 ხდება.
   ეს კლასიკური ხაფანგია.

**gdb-ით გადამოწმება:** `p $rax`, `p $rbx` სამივე ნაბიჯის შემდეგ.
ჩაწერე ცხრილი ქაღალდზე: | ნაბიჯი | rax | rbx |. ბოლოს `rax=20`, `rbx=10`.

**ხშირი შეცდომები:**

- შუალედური ნაბიჯის შედეგი არასწორ რეგისტრში ჩაიწერა.
- იგივე რეგისტრი ორივე მხარეს.
- გაცვლის შემდეგ exit-ად ძველი მნიშვნელობა გამოიყენე.

**დაფიქრდი:** რატომ არის ეს მეთოდი დღეს **ცუდი პრაქტიკა** რეალურ კოდში,
თუმცა მასწავლებლად შესანიშნავია? (მინიშნება: CPU-ს pipeline და
დამოკიდებულებები.)

## w2d5_calculator · კალკულატორი (მინი პროექტი)

**სამიზნე:** სრული პროგრამა: წაიკითხე `12 + 30`, გამოთვალე, დაბეჭდე შედეგი.

**სცენარი:** ტესტი 5 შემთხვევას ამოწმებს:

| შეყვანა | მოსალოდნელი გამოსავალი |
| --- | --- |
| `12 + 30` | `42` |
| `100 - 58` | `42` |
| `6 * 7` | `42` |
| `84 / 2` | `42` |
| `5 - 20` | `-15` |

**იდეები:**

1. დაშალე პრობლემა **ნაბიჯებად** და თითოეული ცალკე შეამოწმე gdb-ში:
   read → atoi(პირველი) → ოპერატორი → atoi(მეორე) → ოპერაცია → itoa → write.
2. `read`-ის შემდეგ ბუფერში **newline-იც** წერია. `atoi` მასზე გაჩერდება —
   ეს სწორედ ის ქცევაა, რაც გჭირდება, რომ შემდეგ ოპერატორზე გადახვიდე.
3. `atoi`-მ **ორი** მნიშვნელობა უნდა დააბრუნოს: რიცხვი და ახალი მაჩვენებელი
   (სად შეჩერდა). ABI-ით მეორე `rdx`-ში ბრუნდება. ამის გარეშე ვერ იპოვი
   ოპერატორს.
4. `*` შეიძლება `imul`-ით, `/` — `idiv`-ით (მახსოვს: `rdx` განულება ან
   signed გაფართოება `cqo`-თი).
5. `-` ნიშანი: თუ რიცხვი მინუსით იწყება, გამოტოვე ის და ბოლოს შეცვალე
   ნიშანი. `-15`-ის დასაბეჭდად `itoa`-ს უარყოფითის მხარდაჭერა სჭირდება.
6. **დაბეჭდე მხოლოდ შედეგი.** ტესტი ბოლო ხაზს ადარებს, ამიტომ დამატებითი
   ტექსტი შედეგამდე ხელს არ გიშლის, მაგრამ შედეგი ბოლოს უნდა იყოს.

**gdb-ით გადამოწმება:** `read`-ის შემდეგ `x/16cb &input` — ნახე ზუსტად რა
ბაიტები მოვიდა (მათ შორის `\n` = 10). პირველი `atoi`-ს შემდეგ შეამოწმე
ორივე დაბრუნებული მნიშვნელობა. `itoa`-მდე ნახე ბუფერი.

**ხშირი შეცდომები:**

- `read`-ის შედეგი (`rax`) არ შემოწმდა — თუ 0 ბაიტი მოვიდა, პროგრამა
  ნაგავს ამუშავებს.
- მეორე რიცხვის ძებნა პირველის დასაწყისიდან დაიწყე → ოპერატორი ვერ იპოვე.
- `rax`/`rdx` ერთდროულად დაგჭირდა და ერთი დაკარგე — დროებით სტეკზე შეინახე.
- `idiv`-მდე `rdx` არ გაასწორე (უარყოფითზე `cqo` საჭიროა).
- `atoi` ცარიელ სტრიქონზე 0-ს აბრუნებს და ეს ლეგიტიმური შედეგია — გაითვალისწინე.

**დაფიქრდი:** რას გააკეთებს შენი კალკულატორი შეყვანაზე `12/0`? `abc`? `12+`?
დაწერე ეს შემთხვევები და გადაწყვიტე, შეცდომა გამოაჩინო თუ 0 დააბრუნო.

## w3d2_sum_array · sum_array(int*, size_t) C-დან

**სამიზნე:** asm ფუნქცია, რომელსაც C-ის `main` იძახებს.

**სცენარი:** driver გადასცემს `{1,2,3,4,5}`-ს და ბეჭდავს ჯამს → stdout `15`.

**იდეები:**

1. სიგნატურა: `long sum_array(int *arr, size_t n)`. System V-ით `rdi` = მასივის
   მისამართი, `rsi` = ელემენტების რაოდენობა, დაბრუნება `rax`.
2. **მთავარი ხაფანგი:** `int` არის **4 ბაიტი**, არა 8. ამიტომ ინდექსირება
   `[rdi + rcx*4]`. თუ `*8` დაწერ, მასივის გარეთ წახვალ და ნაგავს შეკრიბავ.
3. ფუნქცია C-ისთვის უნდა იყოს ხილვადი — ამიტომ საჭიროა `global sum_array`
   (და `extern` C-ის მხარეს, რასაც driver თვითონ აკეთებს).
4. `default rel` დაგეხმარება მისამართვაში, თუმცა `-no-pie` ლინკვისას აბსოლუტური

## w3d3_sum_ids · struct-ების მასივის ჯამი

**სამიზნე:** struct-ების მასივზე გავლა და მხოლოდ `id` ველის შეკრება.

**სცენარი:** `struct Item { int id; char flag; double value; }`, 3 ელემენტი
`id = 10, 20, 30` → stdout `60`.

**იდეები:**

1. **ჯერ ზომა გამოთვალე ხელით.** ველები: 4 + 1 + 8 = 13, მაგრამ პროცესორს
   `double` სჭირდება 8-ის ჯერად მისამართზე. ამიტომ კომპილერი ამატებს
   **padding**-ს → struct არის 16 ბაიტი.
2. აქედან გამომდინარეობს: ელემენტებს შორის ნაბიჯი **16**-ია. მასივში
   `arr[i]` მისამართია `base + i*16`.
3. `id` პირველი ველია → offset 0. ამიტომ წაკითხვა `[rdi + rcx*...]`, სადაც
   scale = 16. (x86 scale მხოლოდ 1, 2, 4, 8 იცის — 16-ისთვის საჭიროა
   ცალკე გამოთვლა ან shift.)
4. შედეგის ტიპი driver-ში `long`-ია — `rax` მთლიანად უნდა დაბრუნდეს.

**gdb-ით გადამოწმება:** `p sizeof(struct Item)` C-ში (ან `p sizeof(...)` gdb-ში
დრაივერთან ერთად) და შეადარე შენს 16-ს. `x/6gx $rdi` — ნახე სამი ელემენტის
ლეიაუტი: სად ზის `id` და სად `double`.

**ხშირი შეცდომები:**

- ნაბიჯი 13 (padding-ის იგნორირება) → მეორე ელემენტიდან ნაგავი.
- offset 0-ის ნაცვლად `id`-ს სხვა ადგილას ეძებ (ის პირველია, მაგრამ
  შეამოწმე!).
- `double`-ს როგორც 8-ბაიტიან მთელ რიცხვს კითხულობ — ტიპები არ ემთხვევა.
- საზღვრის შემოწმება არ არის: `n=0`-ზე ციკლი მაინც უნდა იყოს უსაფრთხო.

**დაფიქრდი:** რას მოხდებოდა, ველების რიგი რომ შეცვალო
(`{char, int, double}` ან `{double, int, char}`)? გამოთვალე ზომები და
შეამოწმე. ეს არის struct-ის დიზაინის რეალური გადაწყვეტილება.

**წყარო:** `03-week3-c-interop.md` § III დღე

## w3d4_simd_add · float მასივების შეკრება SSE-ით

**სამიზნე:** ორი `float` მასივის შეკრება 4-4 ელემენტიანი ბლოკებით + tail.

**სცენარი:** 6 ელემენტი: `a={1,2,3,4,5,6}`, `b={2,3,4,5,6,7}`; driver ბეჭდავს
შედეგის ჯამს → stdout `48.00`. (შედეგი `{3,5,7,9,11,13}`.)

**იდეები:**

1. SIMD-ის იდეა: ერთი ინსტრუქცია, **ოთხი** float ერთდროულად. 4 float = 16
   ბაიტი = ერთი `xmm` რეგისტრი.
2. სიგნატურა: `void add_float(float *dst, float *a, float *b, unsigned long n)`
   → `rdi, rsi, rdx, rcx`. (მაჩვენებლები მთელი რიცხვებია, ამიტომ xmm-ები არ
   გამოიყენება არგუმენტებისთვის.)
3. ციკლი მიდის `n/4` ბლოკზე. დარჩენილი `n % 4` ელემენტი **tail**-ია და
   ცალკე სკალარულ ციკლს მოითხოვს — თუ გამოტოვებ, ბოლო ელემენტები არ
   დაემატება.
4. `movaps` მოითხოვს 16-ბაიტიან **გასწორებას** (aligned), `movups` — არა.
   თუ `movaps`-მა არაგასწორებულ მისამართზე მიმართა → SIGSEGV.
5. არითმეტიკა: `addps` ამატებს ოთხივე float-ს ერთდროულად.

**gdb-ით გადამოწმება:** `p $xmm0.v4_float` — ოთხივე float ერთ რეგისტრში.
ტესტისთვის სასარგებლო ხრიკი: `p $xmm0.v4_float[0]` ცალკეული ელემენტისთვის.
ნახე, როგორ იცვლება ციკლის გავლებზე. `info registers xmm0` ნედლ ბაიტებს
გაჩვენებს.

**ხშირი შეცდომები:**

- tail გამოტოვე → ჯამი 48-ის ნაცვლად 33.
- `movaps` არაგასწორებულ მისამართზე → SIGSEGV (სცადე `movups` და ნახე, რომ
  მუშაობს — ეს არის გაკვეთილი alignment-ზე).
- `% 4`-ის ნაცვლად `n`-ის ზუსტი გაყოფა ჩათვალე.
- ბლოკების რაოდენობა არასწორად დაითვალე (off-by-one ინდექსებში).
- ოპერანდების რიგი: `addps`-ს არ აქვს მნიშვნელობა, მაგრამ `subps`-ს აქვს.

**დაფიქრდი:** რამდენჯერ ნაკლები ინსტრუქცია სჭირდება SIMD ვერსიას სკალარულ
ვერსიასთან შედარებით 1024 ელემენტზე? რატომ არ არის სიჩქარე ზუსტად 4-ჯერ
მეტი?

**წყარო:** `03-week3-c-interop.md` § IV დღე

## w4d1_bufov · buffer overflow → secret

**სამიზნე:** ააგე მოწყვლადი პროგრამა და exploit, რომელიც `secret`-ს გამოიძახებს.

**სცენარი:** ორი ფაილი:

| ფაილი | რა უნდა იყოს |
| --- | --- |
| `solutions/w4d1_vuln.c` | 64-ბაიტიანი `buffer`, `secret()` ფუნქცია, რომელიც ბეჭდავს მარკერს, და კითხვა შეყვანიდან |
| `solutions/w4d1_exploit.py` | payload, რომელიც stdout-ში იწერს |

`secret()`-მა უნდა დაბეჭდოს ზუსტად `SECRET_REACHED` — უნიკალური მარკერი.
ეს პრაქტიკული წესია: ტესტირებისთვის მარკერი ზოგად „შესრულდა“ ტექსტზე
სჯობს, თორემ ვერასდროს გაიგებ, კონტროლი მართლა იქ მოხვდა თუ არა.

**იდეები:**

1. სტეკზე ფუნქციის ჩარჩო ასეა: `[buffer][saved rbp][return address]`.
   Return address-ის გადაწერა ნიშნავს `ret`-ის „შეცვლას“ — ეს არის მთელი
   შეტევის იდეა.
2. რამდენი ბაიტი სჭირდება return address-მდე? **თვითონ გაზომე**, ნუ
   ჩათვლი: `gdb` → `break` სავარაუდო ფუნქციაზე → `info frame` → `saved rip at
   0x...`. სხვაობა `$rsp`-სა და ამ მისამართს შორის = offset.
3. მისამართი **little-endian** წესით ჩაიწერე (უმცროსი ბაიტი პირველი).
   `objdump -d -M intel` ან `nm` გაჩვენებს `secret`-ის მისამართს. `-no-pie`
   აუცილებელია, თორემ მისამართი ყოველ გაშვებაზე იცვლება.
4. `fgets(buffer, 256, stdin)` **იგივე** მოწყვლადობას იძლევა (64-ბაიტიან
   ბუფერში 256-ის კითხვა) და თან პორტაბელურია. თუ შენს სისტემაზე `gets`
   აღარ არსებობს, ეს გამოიყენე.
5. ტესტი შენს `exploit.py`-ს პირდაპირ უშვებს და stdout-ს მილს აძლევს
   პროგრამას — ამიტომ სკრიპტმა payload მხოლოდ stdout-ში უნდა დაწეროს.

**gdb-ით გადამოწმება:** `break vulnerable`, `run < payload.bin`,
`x/40gx $rsp`. ნახე, სად ზის return address და რა ჩაწერე იქ. `ret`-ზე
`stepi` — უნდა აღმოჩნდე `secret`-ის დასაწყისში.

**ხშირი შეცდომები:**

- canary არ გამორთე → `*** stack smashing detected ***`.
- PIE ჩართულია → მისამართი უცნობია (`-no-pie` დააყენე).
- offset არასწორი (71 ან 73, არა 72) — თუ შენი ბუფერი სხვა ზომისაა,
  offset-იც სხვაა; გაზომე, ნუ დაიმახსოვრე.
- byte order შებრუნებული → მისამართი ნაგავია.
- ASLR: თუ stack-ის მისამართს იყენებ (shellcode), სცადე `setarch -R ./vuln`.

**დაფიქრების კითხვა:** რომელი **ორი** დაცვა ამ პროგრამაში გამორთე და

## w4d2_crackme · crackme-ის ამოხსნა

**სამიზნე:** იპოვე, რა პირობას ამოწმებს პროგრამა, და გაიარე იგი.

**სცენარი:** აიღე 2-3 მარტივი crackme (crackmes.one, საწყისი დონე) და
**თითოეულზე ჩამოწერე**:

- რა ტიპის შემოწმება იყო (პირდაპირი შედარება, hash, სიმბოლო-სიმბოლო ციკლი…)
- სად იპოვე ის (ფუნქცია, ინსტრუქცია)
- როგორ გვერდი აუარე (სწორი პაროლი, ან პირობის შეცვლა)

**იდეები:**

1. დაიწყე **ჩვევად** ქცეული თანმიმდევრობით: `strings`, `file`, `nm`,
   `objdump -d -M intel | less`. ხშირად პასუხი პირდაპირ ჩანს.
2. Ghidra-ს decompiler აჩვენებს C-ის მსგავს კოდს — კითხვა ბევრად
   იოლია. მაგრამ decompiler **ცდება** ოპტიმიზაციისას, ამიტომ საბოლოო
   სიმართლე asm-შია.
3. თუ პროგრამა `strcmp`-ს იძახებს, მარტივი გზა არსებობს: `break strcmp` და
   შეხედე არგუმენტებს — მათ შორის შეიძლება უკვე იყოს სწორი პაროლი.
   ეს არის „აპი-ზე დაკვირვების“ ტექნიკა.
4. `ltrace`/`strace` გაჩვენებს ბიბლიოთეკის გამოძახებებს — ზოგჯერ საკმარისია.

**გადამოწმება:** შენ მიერ ნაპოვნი პაროლი მართლა მუშაობს? თუ პირობა
შეცვალე — ცვლილება ახსენი (რომელი ბაიტი და რატომ).

**დაფიქრების კითხვა:** რატომ არის „პაროლის ჩაშენება“ (hardcode) ცუდი
დაცვა, მაშინაც კი თუ დაშიფრულია? რა არის ჰაშირება და რას არ წყვეტს ის?

**წყარო:** `04-week4-reverse-engineering.md` § II დღე

## w4d3_jit · .NET JIT-ის asm

**სამიზნე:** ნახე, როგორ კოდს აწარმოებს JIT კომპილატორი და შეადარე შენსას.

**სცენარი:** C#-ში დაწერე მარტივი ციკლი (ჯამი, მაქსიმუმი, ან სტრიქონის
ძებნა), ნახე JIT-ის asm და **იპოვე 3 განსხვავება** შენს ხელნაწერ NASM
ვერსიასთან.

**იდეები:**

1. `DOTNET_JitDisasm` გარემოს ცვლადი ჩართავს JIT-ის მიერ გენერირებული კოდის
   დაბეჭდვას. ზუსტი სინტაქსი ნახე `04-week4 § III დღე`-ში.
2. მოძებნე ის, რასაც შენ **ხელით არ წერ**: bounds check (მასივის ინდექსის
   შემოწმება), null check, არაპირდაპირი მისამართვა.
3. შეადარე ინსტრუქციების **რაოდენობა** — JIT არ ცდილობს მინიმუმს, ის
   ცდილობს უსაფრთხოებას.
4. ეს არის პასუხი კითხვაზე „რატომ არის C# კოდი ნელი C-თან შედარებით?“ —
   ნაწილობრივ. ნაწილობრივ კი JIT უკეთესს აკეთებს, ვიდრე AOT კომპილატორი.

**გადამოწმება:** ჩამოწერე სამი კონკრეტული განსხვავება ინსტრუქციის დონეზე.
„ნელია“ არ ითვლება — საჭიროა „X ინსტრუქცია, რომელიც Y-ს ამოწმებს“.

**დაფიქრების კითხვა:** თუ JIT-ს აქვს runtime ინფორმაცია, შეუძლია გააკეთოს
